## 2. Per-bug detail

### 2.1 FL-001 — the denominator

**The code.** Three copy-pasted cutoffs, `app.jsx:5612` (intake), `5619` (weigh-ins), `5649` (body
measurements):

```js
const cutoff = new Date(Date.now() - days * 86400000).toISOString().split("T")[0];
return history.filter(d => d.date >= cutoff);
```

Two independent defects in one expression, and it is worth separating them because they need
different tests.

**(a) Inclusive `>=` over an N-day subtraction yields N+1 keys.** Today 2026-09-13, `days=7` →
cutoff `2026-09-06` → rows 06,07,08,09,10,11,12,13 = **8**. Then `app.jsx:6077-6078` divides by
`filtered.length`:

- kcal `2665+2580+2334+2228+2504+2927+2331 = 17569`; `/7 = 2509.9 → 2510`; `/8 = 2196.1 → 2196` ✔
- fat `67+72+80+80+83+79+83 = 544`; `/7 = 77.7 → 78`; `/8 = 68.0 → 68` ✔ (exact, which is why the
  founder's cross-check on fat is good evidence)
- protein `180×7/8 = 157.5 → 158` ✔ carbs `200×7/8 = 175` ✔ — all four, as reported.

**(b) `toISOString()` is UTC.** The effect is time-of-day dependent, which matters enormously for
test design. In BST (UTC+1), local day `D` hour `h`: the UTC instant is `D,h−1`, or `D−1,23` when
`h=0`. Subtract 7 days → UTC date `D−7` when `h ≥ 1`, `D−8` when `h = 0`.

> **So the bug is "divided by 8" all day, and "divided by 9" between 00:00 and 00:59 local.**
> In GMT (after 25 Oct) it is a stable 8. West of UTC it would flip to 7 and silently *drop* the
> oldest day instead.

A test that asserts "8 rows" is therefore **timezone- and hour-dependent**, which is precisely how
this class of bug evades suites.

**Two things make this worse than an ordinary off-by-one:**

1. **The correct engine already exists in the same file and is already tested.**
   `weeklyIntakeScore` (`app.jsx:614-651`) divides by `daysUsed = days.filter(d => d.loggedAnything).length`
   (618-619, 627) — it *excludes* the zero-row. And `__tests__/logic.test.js:3468-3478` is literally
   the test *"an unlogged day is excluded from the average, not counted as a favourable zero"*, with
   the comment "the exact inversion guardrail §6 exists to prevent." The History card is a second,
   wrong implementation of a rule that is written down, implemented correctly, and unit-tested 5,000
   lines away.
2. **There is always a zero-row.** `app.jsx:6985-7008` writes a snapshot for today unconditionally,
   `kcal: Math.round(sumLogs(logs).kcal)` — 0 before the first meal. `history` therefore *always*
   contains a today row, in every range. The extra row is guaranteed, not incidental.

The note at `app.jsx:5667-5671` shows the author **knew**: *"those cutoffs come from a UTC date
string while the day keys are local (they differ for an hour a day under British Summer Time)."*
It was worked around for the join and left in place for the filter, three lines above.

**Fix direction: agreed, with one correction.** "7 days ending at yesterday's midnight, local time"
is right. Don't hand-roll it — `app.jsx:3915-3918` already builds local day keys the DST-safe way:

```js
const d = new Date(Date.now() + getDevDateOffset() * 86400000);
d.setDate(d.getDate() - i);
return dateKey(d);
```

`setDate` is calendar arithmetic, so it is immune to both the UTC bug and DST. Copy that. Note it
also respects `getDevDateOffset()`, which the History cutoffs do not — see §4.3.

### 2.2 FL-002 — weight trend headline

**Confirmed.** `app.jsx:6082-6085`: `first = filteredWeighIns[0]`, `last = filteredWeighIns[len-1]`,
`diff = last − first`. `weighIns` is kept sorted ascending (`app.jsx:6811-6812`) and `.filter`
preserves order, so this is exactly newest − oldest. Live: `"97.1kg → 98.8kg"`, `"+1.7 kg"` in
`var(--bulk)`.

**I disagree with the fix direction as written,** on two counts.

**(a) "Take it from the ends of that line" understates the trend by about 3×.** The line drawn is
`ROLLING` at `app.jsx:5632-5637`: `win = arr.slice(Math.max(0, i-6), i+1)`, drawn once
`win.length >= 3`. On the 7-Days range `arr` has ~7 entries, so **every window is an expanding
prefix** — the first drawn point is the mean of readings 1-3 and the last is the mean of all 7.
Worked example, a perfectly linear series rising 0.1 kg/day across 7 readings (true span change
+0.6):

- mean of first 3 = `p0 + 0.1`
- mean of all 7 = `p0 + 0.3`
- "ends of the line" = **+0.2**, against a real +0.6.

So the proposed figure systematically reports a third of the real movement, and it would read
"+0.2kg" on a week the scale genuinely climbed 0.6kg. That is a worse failure than the current one
for a cut-safety screen, because it understates in the direction the user wants to hear.

**(b) "Just call the dashboard's v78 fix" renders nothing on this data.** The dashboard badge is
`trend7`, `app.jsx:3466-3473`, two `weighRollingAvg(…, 7)` a week apart. `weighRollingAvg`
(`app.jsx:657-661`) returns `null` when fewer than 3 readings precede its cutoff. With the founder's
7 readings (06-13 Sept) the older window is `w.date < "2026-09-06"` → **zero readings** → `null` →
`trend7 === null` → **no badge at all**. The dashboard is currently silent on weight trend for this
exact account; History is loud and wrong. Porting `trend7` as-is swaps a wrong number for a blank.

Also note `trend7` only renders at all when `todayEntry` exists (`app.jsx:3485`) — no weigh-in
today, no trend anywhere. Third inconsistency on the same quantity.

**What to decide before writing a test (this is a blocker, not a detail):** the figure is one of
(i) least-squares slope over the readings in range, reported as kg/week — the founder's own
"+0.87kg/wk vs −0.08kg/wk" arithmetic is exactly this and is the honest answer; (ii) the dashboard's
two-rolling-averages rate, with an explicit "not enough readings yet" state; (iii) the rolling
line's endpoints, which I argue against above. **Pick one and write it into a spec first.** A test
cannot be written against "roughly flat".

**Stale comment, flag it:** `app.jsx:5644-5645` says the body-fat window is by reading count "rather
than weight's calendar-day window." Weight has no calendar-day window — `5633` slices by index and
`weighRollingAvg` uses `.slice(-n)` on readings. The comment describes behaviour that does not
exist. Per the persona, a spec that contradicts behaviour is louder than a missing one.

### 2.4 FL-004 — "check weight still shows today"

**Not a bug. It is an acceptance criterion for FL-001, and it is the highest-risk item in the batch.**
The founder is right to have written it, and right about the principle.

Here is the trap, which I verified: **the whole chart + averages + day-list block is gated on the
intake row count.** `app.jsx:5930`:

```jsx
{range !== "DAY" && filtered.length > 0 && ( … charts, averages, weight trend, day list … )}
```

with the `else` at `app.jsx:6145-6149` → *"No data for this range yet."*

So if FL-001 is fixed by narrowing `filtered` to complete days, then on day one — and on any range
with no complete intake days — `filtered.length === 0`, and **the weight chart, the body-fat chart,
the tape chart and the weigh-in trend all vanish**, along with today's weigh-in. FL-001's fix
silently breaks FL-004, and not one existing test would notice, because no existing test asserts
that the weight chart is present.

**The fix must therefore split three things that are currently one variable:**

| Purpose | Window | Source of truth |
|---|---|---|
| Intake averages denominator | 7 complete days ending yesterday, logged days only | FL-001 |
| Weigh-in / measurement series | the same N days **including today** | FL-004 |
| Whether the block renders at all | any row of *any* kind in range | new — `5930` |

**Can both be asserted in one suite without flakiness? Yes, and the two are not actually in
tension** — they are two windows with two names. The flakiness risk is not the opposing directions;
it is that today's code derives both from `Date.now()` at render time inside a component closure.
Fix that and both become ordinary table-driven assertions. Mechanism in §5.

The founder's third bullet — "each card says which dates it is using" — is already settled project
policy, not a new idea: `features/body/02-founder-decisions.md` DECIDED 3, *"It must state what it
is built from … transparency over suppression."* Cite that in the spec and it needs no re-deciding.

### 2.5 FL-005 — three day counts

**Confirmed** — live output shows all four strings. But one correction to the brief's map and one
disagreement on the fix.

**Map correction.** The brief points FL-005's fourth count at `app.jsx:2455`
(`Still filling in — … of 7 days logged so far.`). That branch does **not** render for this data.
`isFillingIn` requires `weekScore.state === "filling-in"`; with 8 snapshots, `accountIsNew` is false
(`3964`), `totalDays = 7`, `daysUsed = 6 ≠ 0`, so a real verdict is returned and the line that
renders is **`app.jsx:2463`**: `Based on {daysUsed} of {totalDays} days logged`. My run confirms
`"Based on 6 of 7 days logged"`, which is 2463's wording, not 2455's.

**Disagreement on the fix.** The founder's expected outcome is "one consistent count." Two of these
four counts are *correct and deliberate*, and forcing them together would be a regression:

- `"Based on 6 of 7 days logged"` is right. The Dashboard window is `last7Keys` = 7 days **ending
  today** (`app.jsx:3913-3918`), documented at `app.jsx:588`: *"'This week' = the last 7 days ending
  today, not the calendar week."* Of those, 6 have intake; today has none. 6 of 7 is exactly true.
- Critically, the Dashboard's 7 days are **07-13 Sept** and History's 8 are **06-13 Sept**. They
  count *different date sets*. They are not two answers to one question.

So the bug is not "three counts", it is **"three counts and nothing on screen says what any of them
counts."** Fix by labelling, per DECIDED 3, not by unification. And note that after FL-001 there
will legitimately be **three windows** (Dashboard 7-ending-today; intake 7-ending-yesterday;
weigh-ins N-including-today). Unless all three are pinned by tests *and* written into a spec, the
next person to look at this screen will "fix" one into another.

### 2.7 FL-007 — abandoned log vs genuinely low day

**Confirmed as a gap. Not actionable now, and I'd drop it to Low as a defect.**

The stored shape genuinely cannot tell these apart. What exists is a *binary*: `loggedAnything`
(`app.jsx:3953`) = `kcal > 0 || logs.length > 0`. So the app distinguishes "nothing at all" from
"something", and nothing else. A day with breakfast and lunch only is indistinguishable from a
genuinely light day by construction, and no arrangement of existing fields changes that. The founder
is right that this is the bug.

**House rule 5 applies with force.** Any of the candidate signals — a "day complete" flag, a last-log
timestamp, a meal-slot count — is a new stored field, and a column that does not exist in Postgres
makes the whole `syncHistory` upsert fail with no visible error (`app.jsx:1474-1492`; this repo lost
its history sync that way on 2026-09-11, per `app.jsx:868`). This must not ride along with the
FL-001 fix.

**One thing worth saying to the founder:** fixing FL-001 *narrows* FL-007 usefully. Once the
denominator counts only days with intake, the "stopped logging entirely" case is already handled
(the day drops out). What remains is only the genuinely partial day. Smaller problem than the report
implies.

### 2.8 FL-008 — day one

**Confirmed today, before any fix** — so upgrade it out of "to be checked". And the predicted
failure mode is wrong, which matters because the test you'd write for a NaN is not the test that
catches this.

Executed, a fresh account with nothing logged, History opened:

```
"… Day 7 Days 30 Days … 30 DAYS AVERAGES · 1 DAYS  0 KCAL 0g PROTEIN 0g CARBS 0g FAT
  1 DAYS LOGGED  Sun, 13 Sept 2026 CUT P:0g · C:0g · F:0g · 💧0  0 ›"
```

- **No NaN. No crash. No divide-by-zero.** The guard at `app.jsx:6077` (`filtered.length ? … : 0`)
  holds. The founder's predicted symptom does not occur.
- **The actual symptom is worse, because it is confident:** the screen states a 30-day average of
  **0 kcal** on the strength of one empty row. A wrong number that looks like a number beats a NaN
  for causing a bad decision — and "what does the one person need to see to make a correct decision
  about his own body" is the whole test here.
- **Two empty states are dead code.** `app.jsx:5724-5729` (*"No history yet — days auto-save as you
  log."*) and `app.jsx:6145-6149` (*"No data for this range yet."*) are both unreachable on a live
  account, because `app.jsx:6985-7008` creates today's snapshot before History is ever opened. I
  confirmed the second one directly: a single row 400 days old, range 7 Days, still renders
  `"7 DAYS AVERAGES · 1 DAYS / 0 KCAL"` rather than the empty state. An empty range does not show
  its empty state *anywhere*.

So FL-008 is not "a hole the FL-001 fix will open", it is a hole that is open now, and the FL-001
fix changes which branch it falls down (from "0 kcal from 1 row" to "0 complete days").

**The test case for it** — written out, since you asked:

```gherkin

  Background:
    Given a new account created today
    And nothing has been logged yet

  Scenario: The averages card does not claim an average it cannot have

  Scenario: Today's weigh-in survives the complete-days rule   # FL-004's half
    Given I weigh 98.8kg this morning
    When I open History, select "7 Days" and the Weight metric

    And the weight card is not replaced by "No data for this range yet"
```

**Does anything existing cover a zero-row / NaN state on History?** No. Nothing in

### 2.10 FL-010 — a past day's mode cannot be corrected

**Confirmed by code, and the diagnosis is exactly right.** `app.jsx:5757-5762` renders the mode as a
non-interactive `<span>`; `app.jsx:5763-5769`, immediately beside it, renders `training` as a
`<button>` calling `patch({ training: !day.training })`. Food and water are editable on the same
screen. Mode is the one field that isn't.

**Good news first:** `mode` is already a synced column (`app.jsx:1478`, `history_snapshots.mode`), so
**house rule 5 does not bite — no migration needed.** Say that loudly; it is the thing that would
otherwise block this.

**Two traps that will make a one-line fix a silent no-op. Both need tests before the fix.**

1. **The day's stored target is not re-derived, so the rescore doesn't happen.** `patch`
   (`app.jsx:5683-5691`) only recomputes kcal/macros, and only when `p.logs` is passed. It never
   touches `targetKcal`/`targetProtein`/`targetFat`/`targetFatFloor`/`floored`. The Dashboard's
   `weekDays` *prefers the snapshotted target* when present (`app.jsx:3940-3947`) — and every
   snapshot from 2026-09-09 onward has one. So flipping MAINTAIN→CUT leaves the day graded against
   a MAINTAIN target that is 500 kcal higher (`MODES.cut.adj −500` vs `maintain 0`) and a fat target
   at 1.0 g/kg instead of 0.8. **The founder's expected outcome — "Changing it from MAINTAIN to CUT
   rescores that day" — will not happen.** The segment colour will not move. This is the single most
   important thing for the implementer to know, and it is invisible without a test.
2. **Editing *today's* mode in History gets reverted.** `app.jsx:6985-7008` rebuilds today's row
   from live state on `[logs, water, workouts, mode, ready, prof, tdeeAdj, customKcal]` — and `mode`
   there is the live `mode__<todayKey>` state, not the history row. `hist` is not a dependency, so
   the revert is not immediate: the edit survives until the next time anything in that list changes
   (log a meal, tap water), then silently reverts. If the new control is allowed on today's row it
   must write `mode__<todayKey>` via `saveMode` (`app.jsx:6544-6549`), not just `patch`.

**On the open questions at the end of the report** — 1 and 2 are real and need founder answers before
a test can be written. My read: Q1 ("recalculate closed weeks?") is moot for the weekly ring, which
is a rolling 7 days ending today (`app.jsx:588`) and has no "closed" weeks to recalculate; a day
older than 7 days simply falls out of the window. Q3 ("a read-only cut-off") — house rule 1 argues
against adding one; there is no friction-free way to express it.

### 3.1 There is no spec for the History screen. At all.

`logging/`, `profile/`, `targets/`. **There is no `features/history/`.** Every other screen has a

truth for UX decisions. No spec means no stated acceptance criterion, which means there was never
anything for a test to be written against. The founder found FL-001 by eye because by eye was the
only instrument pointed at this screen. **This is the root cause, and it is the one fix that
prevents the next FL-001.**

(The nearest thing that exists, `features/body/02-measurement-feedback-and-history.feature`, is
scoped by `02-founder-decisions.md` §"Scope boundary" to *body data on* History — rows, day detail,
CSV. It explicitly does not cover the averages card. That scoping was correct; it just left a hole
nobody then filled.)

### 3.2 `__tests__/logic.test.js` is a hand-typed mirror, not an import of the code

This is the part I'd most want the implementer to internalise. The file has **zero `require` and
zero `import`** of `app.jsx` — I checked. It opens: *"Pure logic extracted from app.jsx — tests run
in Node via Jest"*, and then **re-declares** `calcTargets`, `computeMacros`, `weeklyIntakeScore`,
`bodyFatWindowChange`, `csvRows` and ~40 more, by hand, with comments like *"Faithful mirror of
app.jsx calcTargets"* (`logic.test.js:39`).

Three consequences, in order of severity:

1. **Code that was never copied in cannot be tested, and nothing reports that.** The History cutoffs
   were never mirrored, so they are outside the suite by construction. 370 green tests carry no
   information about them whatsoever.
2. **The mirror can drift silently.** `logic.test.js` can stay green across a change to `app.jsx`
   that breaks the app, because it is testing a copy.
3. **Coverage numbers are meaningless as reassurance.** "323 tests" (now 370) sounds like a lot. It
   is 370 tests of a transcription.

The deeper cause is architectural: `app.jsx` is one file compiled to a browser script with no module
system, so there is nothing to import. **A standing recommendation, outside this batch and touching
the build: extract the pure layer into a `logic.js` that both `app.jsx` and Jest load.** Until that
happens, every Jest test here is only as good as a manual copy-paste — and that should be stated in
the file's own header, which currently implies the opposite.

### 3.3 The missing class of test: there is no layer that tests a date window

This is the direct answer to "what class of test was missing."

- **Jest** tests pure functions, and the History windows are **not functions** — they are three
  inline IIFEs inside a React component closure (`app.jsx:5609`, `5616`, `5646`), reading
  `Date.now()` at render. Nothing can call them. Not a missing test case: an **untestable shape**.
- **Playwright** tests what the screen says, and **no Playwright test has ever opened the averages
  card.** I grepped the whole of `e2e/` for `AVERAGES`, `DAYS LOGGED`, `WEIGHT TREND`, `7 Days`,
  `30 Days`, `All Time` — **zero hits**. Three specs open History (`body-history`,
  `body-measurements`, `weigh-ins`) and all three stay on the default `30D` range
  (`app.jsx:5593`) and assert only on day rows, the day detail and chart line counts.
- **The fixtures are built so the boundary can never appear.** `e2e/body-history.spec.js:41` seeds
  `history: [day(3), day(2), day(1)]` — three past days, no today row, on a 30-day range. Nothing in
  that shape can expose an N+1 window.

So the missing class is: **a test that pins a date window's edges against a fixed clock.** No test at
either layer does this for any screen.

### 3.4 Do the *tests* fall into the local-vs-UTC trap?

**No — and that is the sharpest irony in the batch.** The test authors got it right and never pointed
the same scrutiny at the app:

- `e2e/harness.js:10-13`, a header comment: *"The app keys the day from LOCAL date parts
  (app.jsx:214), NOT toISOString(), which is UTC. Under BST those disagree between 00:00 and 00:59 —
  a seeded `mode__<key>` would land on the wrong day and the test would pass against a screen that
  was never configured."*
- `e2e/body-history.spec.js:10-11` repeats it for its own `key()` helper.
- `logic.test.js:1281` `dayKeyAgo` uses `dateKey(...)`, the local-safe builder.

The trap is documented twice, in the test layer, in the exact words needed to find FL-001 — while
`app.jsx:5612` does the forbidden thing. **Nobody audited the app for the pattern the harness was
built to avoid.**

### 3.5 The cheapest test that would have caught it already has a template in this repo

`__tests__/styles.test.js` is a **static source-text guard**, written after a silent whole-app bug
(`var(--cut)88`) survived every DOM assertion for weeks. Its header says it is static on purpose
because *"it sees the tints that only appear once you tap to edit a target, **or open History**, or
add an allergy tag — states no test navigates to."*

The repo already invented exactly the right instrument for this class of bug, for exactly this
screen, and never pointed it at dates. A four-line addition in the same style:

```js
describe("Day keys are never derived from UTC", () => {
  test("no toISOString()-derived date key in app.jsx", () => {
    const offenders = codeLines()
      .filter(l => /toISOString\(\)\s*\.\s*split\(\s*["']T["']\s*\)\s*\[\s*0\s*\]/.test(l.text))
      .map(l => `app.jsx:${l.n}  ${l.text.trim().slice(0, 100)}`);
    expect(offenders).toEqual([]);   // today: 5612, 5619, 5649
  });
});
```

It catches half of FL-001 and every future recurrence, costs nothing, needs no extraction, and runs
in milliseconds. I verified the pattern appears at exactly those three lines and nowhere else —
every other `toISOString()` in `app.jsx` (1335, 1347, 1354, 1368, 1389, 1401-1404, 1414-1415, 1422,
1430, 1443, 1450, 1468, 1476, 6768) is a timestamp, which is correct usage and not matched by the
regex above.

**Write this one first. It is the highest value-per-line test in the whole plan.**

### 4.2 The honest answer on "can FL-001 and FL-004 live in one suite"

Yes, and they are not actually opposed — they are two named windows over the same data. What makes
them look opposed is that today's code derives both from one `Date.now()` call at render time. Three
mechanisms, in order of preference:

1. **An injected clock on a pure function — the main mechanism, and the repo already does this.**
   `bodyFatWindowChange(measurements, sex, asOfMs = Date.now(), days = BF_WINDOW_DAYS)`
   (`app.jsx:921`) takes the clock as a defaulted parameter, and `logic.test.js:1358` drives it with
   fixed values. `cutPromptFor` does the same (`logic.test.js:597`: `now = Date.now()`). Extract
   `rangeWindow(range, nowMs)` in that shape and every window assertion becomes a pure table test
   with zero clock dependence. **This is the answer.**
2. **A faked browser clock for the e2e layer.** Playwright is 1.62.1, so `page.clock` is available
   (`page.clock.install({ time })` / `setFixedTime`). Combined with
   `test.use({ timezoneId: "Europe/London" })` this makes the 00:30-BST case reachable, which
   `dev_date_offset` cannot reach (it is a whole-day integer — `e2e/harness.js:58`). **Caveat: I did
   not verify `page.clock` against this harness.** `e2e/harness.js` seeds inside `addInitScript`
   using `Date.now()`, so the install must happen before `goto` for the seed and the app to agree.
   Flagging as unverified.
3. **Seeded fixtures relative to real today, no offset.** What `body-history.spec.js` already does
   via its `key(n)` helper. Works, and is the right default for everything except the hour-boundary
   case.

### 4.3 A trap that will silently make an e2e test for FL-001 pass vacuously

**`dev_date_offset` does not move the History range cutoffs.** `app.jsx:5612/5619/5649` read raw
`Date.now()`; they never call `getDevDateOffset()`, which `todayKey()` (`app.jsx:214-220`) and
`last7Keys` (`app.jsx:3915`) both do. The harness seeds day keys relative to
`Date.now() + off * 86400000` (`e2e/harness.js:76`, `116`).

So with `dayOffset: 5`, the seeded rows run from real-today+5 back to real-today−2, while the cutoff
sits at real-today−7. **Every seeded row clears the cutoff regardless**, and the off-by-one becomes
invisible. A test written that way would go green against the broken code and stay green forever.

Same defect in `trend7` (`app.jsx:3466-3473`) — bare `new Date()`, no dev offset — and in
`bodyFatWindowChange` as called at `app.jsx:5665` (default `asOfMs = Date.now()`). So the dashboard
weight trend and the body-fat window card also ignore the simulated clock.

> **Rule for the implementer: no History range test may use `dayOffset`.** Seed relative to real
> today. If the fix makes the cutoffs honour `getDevDateOffset()` — it should, for consistency with
> `todayKey` — then that itself needs a test, and only then does `dayOffset` become usable here.

### 4.4 A fixture gotcha I hit, which will cost the implementer an hour

**You cannot seed a non-zero row for today through `history`.** `app.jsx:6985-7008` overwrites
today's snapshot from live state (`sumLogs(logs)`) as soon as `ready` is true. I seeded
`history: [{ date: today, kcal: 600, … }]` and the screen showed `0 KCAL` and `P:0g · C:0g · F:0g`.
That is the harness working correctly, not a bug.

To give today real intake, seed `logs` — the harness writes it to `logs__<todayKey>`
(`e2e/harness.js:87`) and the app derives today's row from it. Past days seed fine through
`history`. This is also *why* the founder's captured state has today at 0 kcal: it is the natural
state of an unlogged morning, and it is present in every range on every account.

## 6. Missing bugs this batch implies but does not name

Separated by what I executed versus what I reasoned, because at n=1 the difference decides whether
it is worth anyone's time.

### Real — verified by running it

1. **The off-by-one is on every range, not just 7 Days. `30D` shows "30 DAYS AVERAGES · 31 DAYS",
   KCAL `2323`.** Arithmetic: 30 complete days at 2400 + today's 0 = `72000/31 = 2322.6 → 2323`,
   against a correct `2400`. The founder has 8 days today; in three weeks he has 31 and the 30-day
   card is wrong by the same mechanism. `3M` → 91 rows, `1Y` → 366 rows. **Not theoretical — fix all
   four with A2, one table test.**
2. **"All Time" is diluted by the zero-row too.** One row 400 days old + today's empty row →
   `ALL TIME AVERAGES · 2 DAYS`, average `2000/2 = 1000`. The worst ratio of the lot, because `ALL`
   is where a single real day is most likely to sit alone.
3. **The empty-range state is unreachable.** One row 400 days old, range 7 Days → `"7 DAYS AVERAGES
   · 1 DAYS / 0 KCAL"`, not `"No data for this range yet."` (`app.jsx:6145`). Today's auto-created
   row is in every range, so that branch is dead. Same for the `history.length === 0` empty state at
   `app.jsx:5724`. **Two dead empty states** — and the founder's FL-008 expectation ("an empty state
   saying averages start once the first full day has finished") is asking for a string that does not
   exist and, in the current structure, could never render.
4. **The body-measurement cutoff (`app.jsx:5649`) has the identical defect and is uncommitted work
   from this week.** The bug was copy-pasted a third time while the body/02 feature was being
   built, into the file that carries the comment explaining why it is wrong. Fix all three from one
   `rangeWindow`, and make A2 cover all three consumers.
5. **FL-009 affects the intake charts too, not just body charts.** `app.jsx:6039` (line) and `6046`
   (bar) use the same categorical `dataKey="date"`. Today `filtered` has one row per stored day, so
   gaps are rare for intake — but a day the app was never opened has no snapshot, and that day's
   absence would close up invisibly. Lower priority, same fix.

### Real but lower priority — reasoned, not executed

6. **The weigh-in and intake windows are already inconsistent with each other, before any fix.**
   `filteredWeighIns` (`5619`) applies the intake window to weigh-ins, so the weight chart silently
   shows 8 days of readings under a "7 Days" label. FL-004 will formalise the split; right now it is
   an accident that happens to look like the desired behaviour.
7. **The CSV export ignores the range filter.** `csvRows(history, weighIns, bodyMeasurements)`
   (`app.jsx:5696`) takes the full arrays, so `📥 CSV` exports everything regardless of the selected
   range. I think that is *correct* — an archive should be complete, and `csvRows` is properly tested
   at `logic.test.js:1394` — but it is undocumented and nothing asserts it. **One cheap test: the
   export is unchanged by the range filter.** It costs nothing and stops a future "fix" from
   range-scoping the archive. The export does include today's partial row, which for an archive is
   right (it is what is stored).
8. **The Day view's `dayIdx` initialises from `history.length - 1` (`app.jsx:5599`) — today's row.**
   So tapping "Day" lands on a row that is mid-day by definition. Consistent with FL-001's theme
   (today is treated as a finished day) but not itself wrong, since the Day view reports one day's
   totals rather than an average. Worth one scenario stating that the Day view deliberately *does*
   show today.
9. **DST.** `Date.now() − days*86400000` is a fixed-ms subtraction; across 25 Oct 2026 it lands an
   hour off in local terms, adding one more hour-wide window of wrongness to (b). Small, but A5
   costs one line and the `setDate` fix removes the whole class. **Cover it because it is cheap, not
   because it is likely.**

### Theoretical at n=1 — note and move on

10. **Non-UK timezones.** West of UTC the same code drops the *oldest* day instead of adding an extra
    one. Irrelevant to the one user — **except for one thing that is not irrelevant: a test that
    asserts a row count inherits the runner's timezone.** `playwright.config.js` sets none. That is
    why §5 pins `timezoneId` even though the app only ever runs in the UK.
11. **Leap years / 3M spanning February.** `setDate` handles it; `ALL`'s `99999` days is ~273 years
    and fine. Mentioned only so nobody spends time on it.
